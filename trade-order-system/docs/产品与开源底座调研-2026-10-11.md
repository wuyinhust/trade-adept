# 外贸订单系统：产品与开源底座调研

调研日期：2026-10-11。对象：Grandware，约 10 位使用者、4 个经营主体。

本报告读取了项目需求 Markdown，并抽查 `js/auth.js`、`js/cloud.js` 的权限过滤与追加保存入口；产品信息来自官方文档、官方方案和上游 GitHub。没有安装候选系统、试跑真实业务、联系销售或迁移现有数据。下文的推荐是选型判断；官方列出的能力与通过我们业务验收是不同状态。

## 1. 推荐

**先验证 ERPNext，NocoBase 作为轻量候选；同时用富通天下评估直接采购能省下多少实施工作。** Odoo 是完整 ERP 路线的备选，特别适合能找到合适实施方的情况。monday.com 适合作为协作体验参照，Salesforce 适合作为数据权限与业务对象参照。

这个项目的核心是客户订单、多工厂采购、生产节点、出运、收付款和利润计算。能复用这些业务对象与关系，比换一个漂亮的 CRM 页面更能减少开发量。

建议优先复用成熟系统的用户认证、服务端权限、主数据、销售采购单据、编号、持久化和导入导出；新增代码集中在国内/HK 两套管理利润、验货和出运字段、团队范围及少量专用报表。先试原生界面，确认业务适配后，再决定是否接回现有 Grandware 界面。

## 2. 选型必须覆盖的实际需求

依据项目的 [完整开发需求文档](../外贸订单系统-完整开发需求文档.md)：

| 项目要求 | 选型时的判断重点 |
| --- | --- |
| 2 个国内主体、2 个香港主体 | 同一系统能管理多公司，按公司采用不同币种与利润口径 |
| 管理员、财务、经理、业务员、单证员 | 服务端区分角色、团队、公司、负责人和创建人；同时控制成本字段 |
| 一张客户订单对应多个工厂 | 需要销售单和多个采购/工厂任务的关联，不能只存订单总额 |
| 订单、收款、出运三类状态 | 各状态可以独立推进，并能形成关联进度 |
| 国内退税管理利润、HK 纯 USD 利润 | 必须按现有业务定义定制，不能直接拿标准 ERP 毛利替代 |
| 客户有多个联系人 | 联系人要有独立身份；多人新增、编辑、删除不能互相覆盖 |
| Excel 历史数据、筛选导出 | 需验证实际模板、关联字段映射和导出权限 |
| 自动保存、保存失败提示、10 人并发 | 必须做真实场景测试；关系型数据库本身不能证明不会发生业务覆盖 |

项目文档描述的前端过滤和追加快照保存，与抽查到的本地代码入口一致；线上实际配置与安全规则未核验。本次不沿用历史记忆作为架构结论。

## 3. monday.com 与 Salesforce

### monday.com：参考协作流程，也可以购买后配置

官方提供面向批发团队的订单、库存和财务 CRM 模板，平台 API 可操作 boards、items、字段和用户。可以参考其关联表、状态列、负责人、提醒和多种视图。[批发模板](https://monday.com/crm/marketplace/category/wholesale)、[API](https://developer.monday.com/api-reference/docs/basics)。

对我们的限制：没有找到官方证据证明这些模板直接满足多工厂采购、国内/HK 两套利润和指定权限例外。细粒度板级角色与限制还需核对 Enterprise/当前对应套餐；官网部分页面使用 Ultimate 名称。预算需包含所需产品、席位、自动化额度和实施，而不能只比较起步价。[Enterprise 权限](https://support.monday.com/hc/en-us/articles/31152393208466-Board-permissions-on-Enterprise)、[当前价格](https://monday.com/pricing)。

**判断：协作体验值得参考；如果采用 SaaS，需要先证明业务配置量比 ERP 路线少。**

### Salesforce：参考权限与对象关系，现阶段优先级较低

Salesforce Order Management 有独立的订单履约与售后工作流、Flow 和 API，官方实施资料也涉及对接 ERP。不能把 Sales Cloud 中有订单对象，理解为已经购买了完整 Order Management 或外贸 ERP。[实施说明](https://trailhead.salesforce.com/content/learn/modules/scom-order-management/scom-som-get-started)、[订单产品价格](https://www.salesforce.com/commerce/order-management/pricing/)。

值得参考的是对象权限、记录共享、字段权限分开控制。自定义 Apex 还必须显式执行相应权限，不能认为平台会替开发代码自动处理全部边界。[官方访问控制说明](https://developer.salesforce.com/docs/platform/secure-coding/guide/secure-coding-access-control-protect-from-sharing-violations.html)。

**判断：对目前 10 人的项目，我预计许可选型、业务定制和实施工作较多，因此不列为首个验证对象。已有 Salesforce 合同或实施团队时可以重新排序。**

### ERPNext：已有业务链，新增代码应集中在差异部分

官方销售单可向下创建采购、交货、账单与收款相关单据。代码中的 `make_purchase_order_for_default_supplier` 已按供应商分别生成采购单，这与多工厂拆单有可复用关系。[销售单文档](https://docs.frappe.io/erpnext/sales-order)、[采购单生成代码，version-15](https://github.com/frappe/erpnext/blob/version-15/erpnext/selling/doctype/sales_order/sales_order.py)。

公司与其他关联对象可以通过 User Permissions 限定，敏感字段可通过 Perm Levels 控制；团队范围、负责人或创建人的组合条件仍需配置或扩展后测试。[用户权限](https://docs.frappe.io/erpnext/user-permissions)、[字段权限](https://docs.frappe.io/erpnext/changing-the-properties-of-a-field-based-on-role)。

在 Frappe `version-16` 文档保存路径中，`load_doc_before_save()` 使用 `for_update=True` 读取旧记录，`check_if_latest()` 比较修改时间，过期版本抛出 `TimestampMismatchError`。这是可查的冲突检测机制，**不会自动合并两个人的修改**；自定义写入路径同样需要保留这些检查。[保存实现](https://github.com/frappe/frappe/blob/version-16/frappe/model/document.py)。

多币种账务有基础支持，但当前要求的每小时汇率刷新、重算订单管理利润，应单独建模，不能混同已记账单据的金额。[多币种文档](https://docs.frappe.io/erpnext/multi-currency-accounting)。

具体建议：

- 工厂映射 Supplier，客户映射 Customer，联系人独立管理；客户订单关联多个工厂采购单。
- 产品类型需要先决定如何映射 Item，不能直接把现有工厂汇总数组当标准商品明细导入。
- 增加经营主体类型、验货日期、ETD、报关状态、订单管理利润等字段。
- 把规则放入独立 Grandware 扩展应用，减少修改上游核心的升级成本。
- 若后续保留现有前端，使用受权限控制的 API 接入。Frappe 提供 REST API，但字段映射、登录、错误提示和自动保存仍需适配。[API 文档](https://docs.frappe.io/framework/user/en/api/rest)。

部署入口：[frappe/frappe_docker](https://github.com/frappe/frappe_docker)。ERPNext README 的 `pwd.yml` 是一次性演示，不支持安装自定义应用；正式验证差异模块要用适合扩展应用的部署方式。[部署说明](https://github.com/frappe/erpnext)。

### NocoBase：官方已有订单模板，但要评估模板升级方式

官方 Order Management 方案包含报价、订单、出货、发票、分期付款和应收分析，提供整套备份模板的安装入口。因此可以先恢复模板，再修改表和流程。[订单方案](https://www.nocobase.com/en/solutions/all-in-one/sales)。

权限文档明确区分页面过滤和服务端数据范围，支持表、字段与操作控制；经理可见团队、业务员可见负责或创建的数据等组合条件仍需在实际版本中验证。[安全与权限](https://docs.nocobase.com/security/guide)、[操作权限](https://docs.nocobase.com/interface-builder/actions/permission)。

安装文档的实际限制：模板要求 PostgreSQL 16、指定最低版本，推荐 `alpha-full`；通过恢复备份部署，恢复会覆盖目标应用数据，当前升级也会覆盖定制。社区版可使用主要模块，部分商业插件入口缺失；附件存储和 AI 凭据需换为自己的配置。[安装文档](https://docs.nocobase.com/solution/all-in-one/installation)。

**判断：很适合在空白隔离环境里评估轻量工作台。模板的增量升级、生产版本选择和并发写入行为，通过验证后才能决定作为正式底座。**

### Odoo：同时利用官方模块与 OCA

多公司文档说明了共享联系人、公司所属记录和用户公司范围；开发者还需正确处理公司依赖字段与一致性规则。[多公司](https://www.odoo.com/documentation/20.0/applications/general/companies/multi_company.html)、[多公司开发指南](https://www.odoo.com/documentation/18.0/developer/howtos/company.html)。

可继续查这些现成扩展：

- [OCA/sale-workflow](https://github.com/OCA/sale-workflow)：销售工作流、预付款、拆分交期等模块。
- [OCA/purchase-workflow](https://github.com/OCA/purchase-workflow)：采购流程扩展。
- [OCA/multi-company](https://github.com/OCA/multi-company)：多公司相关扩展。

本次 API 快照中，Odoo 默认分支是 `20.0`，以上 OCA 仓库默认分支是 `19.0`。应根据需要的模块选择同一 Odoo 主版本，并核验每个模块的 manifest、依赖和许可。默认分支不能直接混装。

选择 Odoo 商业托管套餐时，多公司会触发从 Standard 到 Custom 的升级；这不等于自托管 Community 的多公司功能收费。[官方套餐说明](https://www.odoo.com/documentation/20.0/applications/general/companies/multi_company.html)。

### Dolibarr 与 Twenty

Dolibarr 官方 README 列出销售、采购、多币种以及用户和组权限，多公司需要额外模块。适合轻量 ERP 备选，但需先证明能实现本项目的成本字段和团队权限。[README](https://github.com/Dolibarr/dolibarr)。

Twenty 提供 CRM 对象、视图、工作流和代码扩展，适合参考客户详情、关系展示与工作台交互。没有取得足够证据证明它能直接替代多工厂外贸订单闭环。[README](https://github.com/twentyhq/twenty)。

## 8. 最小验证范围与决策标准

先用一张脱敏订单跑完整链路，不必先实现所有页面。以下是后续验证清单，本轮没有执行：

1. 建 4 公司、2 团队、5 角色；API、列表、详情、导出均验证公司/团队范围和成本字段。按现需求测试创建人可见例外，而不是只套默认公司规则。
2. 一张客户订单拆给两家工厂，分别更新预付款、验货、出货，保留原订单关联。
3. 国内公司和 HK 公司各跑一笔成本、费用、收款，按现有业务定义核对管理利润。实时管理利润与账务金额分开。
4. 两人同时新增联系人；两人同时修改同一订单；删除后另一人提交旧版本。确认保留修改或明确报告冲突，不能静默覆盖或复活。
5. 10 个账号同时保存不同订单，验证操作单号唯一、记录数量、断网失败提示和重新登录后的持久化。
6. 导入真实结构的脱敏 Excel，核对关联、币种、状态和数量；导出后能继续迁移到其他系统。

通过标准：完成整条业务链、权限实际生效、并发无静默数据损失、差异模块可独立维护，并且升级不需要重做定制。

优先选择能通过以上验证且定制量最小的方案。ERPNext 若必须大量改核心流程，转看 NocoBase 或 Odoo；如果富通天下能直接覆盖主要差异并满足数据出口要求，就比较采购与自托管的实施维护总成本，再决定是否继续开发。
