## 一、项目背景与业务目标

### 1.1 业务背景

Grandware 集团是一家外贸出口企业，旗下有 4 个经营主体（2 个国内公司 + 2 个香港公司）。业务模式为：国内/香港公司接海外客户订单 → 向国内工厂下生产单 → 生产完成后报关出运 → 收款结汇。

在此之前，订单、客户、工厂、出运等信息分散在 Excel 表格中，由 10 位同事分别维护，存在以下痛点：

1. **数据分散**：各人维护自己的 Excel，管理员无法实时看到全局
2. **权限混乱**：业务员能看到所有人数据，报价与成本互相泄露
3. **数据丢失**：Excel 覆盖保存、邮件传输版本混乱
4. **利润核算出错**：国内公司与香港公司结算币种不同，Excel 公式容易算错

### 1.2 系统目标

做一个 **Web 端多人在线协作的外贸订单跟踪系统**，满足：

- 10 位同事同时在线操作，数据实时同步到云端
- 严格的角色 + 团队 + 公司三层权限隔离
- 订单全生命周期管理（下单 → 工厂生产 → 出运 → 收款）
- 自动利润核算（区分国内/香港公司两套公式）
- 数据永不丢失（多用户并发写入不互相覆盖）

### 2.2 数据存储模型（关键设计）

**这是整个系统最核心、也最容易踩坑的部分，接手开发必须理解。**

当前采用 **append-only（追加写）+ 多文档合并** 模型：

```
用户保存 → 写入一个全新文档（不覆盖任何已有文档）
         ↓
加载时：拉取最近 N 条 active 文档
         ↓
       按 updatedAt 降序，逐条合并（相同 id 取最新，数组字段做深度合并）
```

**为什么这样设计**：CloudBase 匿名登录每次会话产生不同的 `_openid`，导致：

- 跨会话无法 PATCH 别人创建的文档（403/404）
- 单文档共享模式会造成多用户互相覆盖

**已知代价**：删除操作需要"墓碑标记"（soft delete）才能不被旧文档"复活"。

### 3.2 权限系统（核心需求，历史 Bug 高发区）

#### 3.2.1 三层过滤链

数据可见性由三层依次过滤：

```
第 1 层：角色层（Auth.canSeeAll()）
   admin / finance → 跳过公司过滤，看全部
   其他角色 → 进入公司过滤

第 2 层：公司层（filterByCompany）
   按 currentCompanyId 过滤
   ⚠️ 但 createdBy === 当前用户 的数据始终放行（兜底）

第 3 层：团队/个人层（Auth.filterOrders / filterCustomers）
   按 visibleCompanyIds + visibleSalespersonIds 过滤
   ⚠️ createdBy 兜底：自己创建的数据始终可见
```

#### 3.2.2 明确需求（用户原话整理）

1. **管理员/财务**：必须能看到所有人创建的所有数据，不受当前选中公司限制
2. **经理**：能看到本团队内**所有成员**创建的数据（含单证员创建的）
3. **业务员**：只能看到自己负责的订单 + 自己创建的客户/工厂
4. **单证员**：能新建订单和客户，且**新建后必须立刻在列表中看到**（历史 Bug：看不到）
5. **任何角色**：自己创建的数据，无论公司归属如何，**必须始终可见**

### 3.3 订单管理

#### 3.3.1 订单数据模型

```
订单 = {
  基本信息：
    id, customerOrderNo（客户订单号）, companyOperationNo（公司操作单号）
    customerId, contactId（客户联系人）
    companyId（所属公司）
    salespersonId（负责业务员）, createdBy（创建人）
  工厂信息（数组，支持多工厂）：
    factories: [{
      factoryId, factoryName, productType（产品类型）
      totalQuantity（总数量）, totalAmount（总金额）
      prepayment（预付款）
      inspectionDate（预计验货日期）, estimatedShipDate（预计出货日期）
    }]
  财务信息：
    orderAmountUSD, orderAmountRMB
    factoryCostRMB（自动汇总所有工厂金额）
    freightCost / insuranceCost / otherCost（按公司类型含义不同）
    totalRevenueRMB, profitRMB, profitRate
  状态：
    orderStatus（订单状态）, paymentStatus（收款状态）, shippingStatus（出运状态）
  时间：
    orderDate, deliveryDate, createdAt, updatedAt
  软删除：
    deleted, deletedAt
}
```

#### 3.3.2 公司操作单号自动生成规则

**格式**：`公司前缀 + 年份后两位 + 业务员姓氏首字母 + 3位序号`

示例：`GR26A001`（国润 2026 年 业务员A 第 1 单）、`WY26A001`

- 新建订单表单中**预填预览值**
- 若用户留空，保存时自动生成
- 需要独立计数器，避免生成全 001

#### 3.3.3 订单列表功能

- 列显示（14 列）：勾选框 / 操作单号 / 客户订单号 / 客户 / 业务员 / 工厂 / 金额 / 收款状态 / 订单状态 / 出运状态 / 下单日期 / 交期 / 利润（财务可见）/ 操作
- 搜索：支持操作单号、客户订单号、客户名、产品类型
- 筛选：订单状态、收款状态、出运状态、业务员
- 多选 + 批量操作：批量改状态（可分别更新订单/收款/出运状态）、批量删除、取消选择
- 导出 Excel：导出当前筛选结果为 .xlsx，中文表头，数值保留数字类型
- 导入 Excel：见 3.3.5

#### 3.3.4 订单详情页

分区卡片展示：

1. **基本信息**：操作单号、客户订单号、客户、联系人、业务员、下单日期、交期、起运港、海外港口（HK）
2. **🏭 工厂信息**：每个工厂一行，6 字段网格（类型/数量/金额/预付款/验货日期/出货日期）
3. **财务明细**：按公司类型显示不同标签和币种
4. **状态卡片**：订单状态 / 收款状态 / 出运状态

顶部操作栏：编辑、删除（有权限才显示）、打印

#### 3.3.5 订单 Excel 导入

- 提供**模板下载**（.xlsx，含示例行，HK 公司工厂成本标 USD）
- 智能表头匹配：支持多种中文别名（如"客户名称"/"客户" 都能匹配 customerId）
- 客户名称自动匹配到 customerId
- 必填字段校验，展示成功/失败/跳过汇总
- 导入完成后提供"刷新列表"按钮

#### 3.3.6 产品名称处理（特殊需求）

**订单表单中不设"产品名称"字段**。产品名称在保存时**自动从各工厂的 productType 拼接生成**（用"、"分隔）。

### 3.7 利润分析

#### 3.7.1 利润计算公式（双轨制，必须严格区分）

**国内公司（CO-GR / CO-WY）**：

```
退税 = (工厂成本RMB / 1.13) × 退税率(%)
利润 = 订单金额USD × 汇率 - 工厂成本RMB
       - 货代费RMB - 保险费RMB - 其他费用RMB
       + 退税
利润率 = 利润 / 订单金额RMB × 100%

⚠️ 注意：美元费用必须先乘汇率换算成 RMB 再扣除
⚠️ 退税公式是 除以 1.13 而不是 乘以 1.13（还原不含税成本）
```

**香港公司（CO-GW / CO-LK）**：

```
利润 = 订单金额USD - 工厂成本USD - 其他费用USD
利润率 = 利润 / 订单金额USD × 100%

⚠️ 注意：HK 公司全程美金，不做任何汇率换算
⚠️ orderAmountRMB 对 HK 公司应等于 orderAmountUSD（不乘汇率）
```

#### 3.7.2 利润分析页功能

- 总营收、总成本（含全部成本项）、总利润、平均利润率 卡片
- 成本结构饼图
- 客户利润分布图（币种符号按公司动态）
- 订单利润明细表
- 导出 Excel（标签币种动态）

### 3.9 汇率管理（按公司独立）

#### 3.9.1 需求

**每家公司有独立的汇率**，不是全局统一汇率。

```
exchangeRates: {
  'CO-GR': 7.25,
  'CO-WY': 7.25,
  'CO-GW': 7.80,    // 实际不使用（HK为USD交易）
  'CO-LK': 7.80
}
rateMetas: { 每家公司独立的元数据：来源、更新时间、是否自动 }
```

#### 3.9.2 自动刷新要求

- **每小时自动更新一次实时汇率**（用户明确要求）
- 启动时自动抓取一次
- 获取到新汇率后**自动重算所有订单利润**（不需要手动点保存）
- 侧边栏显示下次刷新时间（hover tooltip）

## 四、数据可靠性需求（最高优先级）

> 用户原话："数据很宝贵不能丢失"。这块是历史投入最多、Bug 最多的部分，接手开发必须理解全部保护机制。

### 4.1 需求

1. 所有输入的资料**自动保存**，无需手动点保存
2. 退出登录后再登录，数据必须都在
3. 10 位同事同时操作，**任何人的修改都不能丢失**
4. 保存失败必须**明确提示用户**，不能静默失败

### 4.2 已实现的保护机制

| 机制                | 实现                                                                           |
| ------------------- | ------------------------------------------------------------------------------ |
| 防抖保存            | 200ms 防抖，连续操作合并为一次网络请求                                         |
| 显式 flush          | 所有保存调用方显式 `await DB.flush()`，**禁止在 CRUD 方法内部自动 flush**      |
| keepalive           | 页面关闭前用 `fetch keepalive:true` 保存                                       |
| localStorage 安全网 | 写操作前同步写 localStorage，云端成功后清除；加载时恢复未同步数据              |
| 删除标记传播        | localStorage 中 `deleted:true` 的条目不得被恢复                                |
| 多文档合并          | 加载最近 N 条文档，按 updatedAt 合并，contacts 做深度合并                      |
| delete-wins         | 合并时删除标记优先                                                             |
| 轮询保护            | 云端返回 0 条但本地有 → 拒绝覆盖；本地活跃数 > 云端且 30 秒内保存过 → 跳过同步 |
| 保存状态指示        | 侧边栏显示 ⏳保存中 / ✅已保存（3秒消失）/ ❌错误（持久）                      |
| 保存后验证          | 保存成功后立即回读验证                                                         |

### 4.3 已知遗留问题（需接手方修复）

1. **删除可能"复活"**：append-only + 合并模型下，旧文档中的条目可能重新出现（已用软删除缓解，但边界情况仍存）
2. **云端文档膨胀**：每次保存创建新文档，需要清理策略
3. **无真正的行级权限**：当前靠前端过滤，安全规则只能做集合级控制
4. **CloudBase 匿名登录**：每次会话 openid 不同，建议改用自定义登录

## 六、开发规范与约定

### 6.1 字段命名

- 使用小驼峰：`customerOrderNo`、`companyOperationNo`
- 布尔值用 `is`/`has` 前缀或明确语义：`deleted`、`active`
- 金额字段带币种后缀：`orderAmountUSD`、`factoryCostRMB`

### 6.2 日期

- 统一 `YYYY-MM-DD` 字符串格式
- 时间戳用 ISO 8601 字符串

### 6.3 ID 比较（历史 Bug 高发点）

HTML `<select>` 的 value 永远是**字符串**，而数据库中的 ID 可能是**数字**。
所有 ID 比较必须用 `String(a) === String(b)`，**禁止直接用 `===`**。

### 6.4 公司判断

统一通过 `Exchange.isDomesticCompany(companyId)` 判断国内/香港，不要在业务代码里散落 `companyId === 'CO-GR' || companyId === 'CO-WY'` 这类硬编码。

## 八、关键历史问题清单（避免重蹈覆辙）

以下是本系统开发过程中反复出现的坑，接手开发请特别注意：

| #   | 问题                     | 根因                                                            | 正确做法                                      |
| --- | ------------------------ | --------------------------------------------------------------- | --------------------------------------------- |
| 1   | 新建数据刷新后丢失       | CRUD 方法内部 fire-and-forget flush + 调用方又 flush = 双写竞态 | CRUD 只返回结果，**由调用方显式 flush**       |
| 2   | 删除后刷新复活           | append-only 合并模型中旧文档仍含该数据                          | 必须用软删除（tombstones）                    |
| 3   | 浏览器一直用旧代码       | URL 未变，HTTP 缓存命中                                         | 每次发版更新 `?v=XX` 和 `sw.js` CACHE_NAME    |
| 4   | 单证员新建数据看不到     | 公司归属被权限过滤                                              | `_getEffectiveCompanyId()` + `createdBy` 兜底 |
| 5   | 管理员看不到别人数据     | `filterByCompany` 对 admin 也生效                               | admin/finance 跳过公司过滤                    |
| 6   | HK 公司利润虚高          | USD 金额被误乘汇率                                              | HK 公司全程 USD，不换算                       |
| 7   | 国内公司利润虚高         | USD 费用未乘汇率就扣除                                          | 美元费用先换算成 RMB                          |
| 8   | 退税算错                 | 公式写成 `× 1.13`                                               | 应为 `÷ 1.13`（还原不含税成本）               |
| 9   | 联系人被覆盖             | 合并不合并嵌套数组                                              | 合并时对 contacts 做深度合并                  |
| 10  | 编辑订单选不到联系人     | ID 类型不一致（数字 vs 字符串）                                 | 全部用 `String()` 比较                        |
| 11  | 云端旧文档挤掉新文档     | 拉取条数限制 + 幽灵文档堆积                                     | 查询层用 `where({active:true})` 过滤          |
| 12  | 页面卡在加载遮罩         | loadingOverlay 默认 display:flex                                | 默认 `display:none`，JS 控制                  |
| 13  | CSP 缺失域名导致无法保存 | `connect-src` 未包含 tcloudbasegateway.com                      | CSP 必须包含所有实际请求域名                  |
